# GronkBowl

A weekly async multiplayer fantasy football management sim: NFL Head Coach 09-style franchise/coaching depth, crossed with Blood Bowl-style lethal injuries and asymmetric fantasy races.

Full design reference (game design, system architecture, v1 scope lock): see the project's Master Design Document.

## v1 core loop

Regular season (organize your playbook into your own named folders; each scheduled game is played live, one down at a time - both coaches call a play for the current down, async, then it simulates and the next down waits for the next pair of calls) -> once every game is played, Offseason (draft, free agency, trades) -> repeat. See "Live per-down match engine" below for how a down actually gets played.

## Repo layout

- `backend/` - C# / ASP.NET solution: domain models, deterministic match engine, league orchestrator, EF Core persistence, API.
- `frontend/` - React + TypeScript: roster, franchise, playbook/call-sheet builder, draft/market, match replay UI.
- `docs/` - supporting design/technical notes.

On startup the API applies EF Core migrations automatically and seeds a 4-team demo league (Ironclad Reapers/Ironkin, Skysprint Talons/Aelari, Warhide Crushers/Thornhide, Shiverfang Swarm/Skitterkin) plus a starting free-agent pool, **only if the database is empty** - restarting the API does not reset your league.

- `frontend/` has six tabs: **Roster**, **Playbook**, **Call Sheet** (manual only, no auto-fill), **Draft** (start a class, on-the-clock enforcement, rookie wage scale applied automatically), **Market** (sign free agents, propose trades between teams), and **League** (standings, schedule, "Resolve Week" runs the real Engine and renders the summary + box score).
- `GronkBowl.Api` REST surface: `GET /api/teams`, `.../roster`, `.../playbook`, `.../callsheet`, `PUT .../callsheet`, `GET /api/league/standings`, `/schedule`, `POST /api/league/weeks/{week}/resolve`, `GET/POST /api/draft`, `/draft/start`, `/draft/pick`, `GET /api/freeagents`, `POST /api/freeagents/{id}/sign`, `POST /api/trades`.
- **GM-mode flow (Draft, Free Agency, Trades):** a `DraftState` table persists a live draft's pick order (worst-record-first, via `DraftOrderCalculator`) and prospect pool; `DraftController` enforces that only the team on the clock can take an undrafted prospect, and applies `RookieWageScale` automatically. Free agents are derived - any player not on a roster and not part of an active draft class - and signed through the real `FreeAgencyResolver` (a single offer always "wins" its own resolution, same code path a competitive multi-offer market would use). Trades run through `TradeProcessor`'s cap check, refused outright rather than partially applied if either side would exceed its cap. All three were verified end-to-end against the live database: a pick, a signing, and a trade each actually moved a player onto a new roster.
- `GronkBowl.Infrastructure` is the real Persistence Layer: `GronkBowlDbContext` (EF Core + Npgsql/PostgreSQL). Aggregate roots (Player, Play, Team, CallSheet, Season, Match, League, DraftState) are real tables; nested structures that would otherwise need many small join tables (a Roster's depth chart, a Play's assignments, a Call Sheet's situational buckets, a Season's schedule/standings, a Match's event log, a DraftState's pick order/prospect pool) are stored as single `jsonb` columns via a generic `AsJson<T>()` conversion, with a value comparer so EF's change tracking still notices in-place mutations, not just reassignment. Team<->Play is a real many-to-many relation, since the default plays are genuinely shared rows, not copies per team. Verified end-to-end: migrations apply, the API only seeds when empty, and team/roster/standings state survives a full process restart.

Roadmap tasks 1-11 done underneath that UI and persistence layer:

- Core v1 schema in `GronkBowl.Domain` - `Player`, `Team`, `Roster`, `Play`, `CallSheet`, `Match` (carries a `SeasonId`), `Season`, `League`, `DraftState`, `InjuryResult`, `PlayerGameStats`, `PlayerSeasonStats`.

- `Roster` is a depth chart per position (starter/bench are derived views, not separate lists), so a mid-game injury auto-resolves to "next man up," and a new acquisition (`AddToDepthChart`) always joins at the bottom, not ahead of players already there.
- `GronkBowl.Engine.CasualtyResolver` implements the two-stage Casualty & Injury Table (armor check, then severity roll), deterministic given a seeded `Random`.
- `DefaultPlaybook` seeds the 5 offense / 5 defense starter plays every team ships with. `CallSheet.SelectPlay` picks a play by situation with a Standard-bucket fallback.
- `GronkBowl.Engine.MatchEngine.ResolveGame(...)` is the pure `resolve()` function from the design doc: two teams, their call sheets, and a seed in; a fully resolved `Match` with a populated, self-describing `EventLog` out. Verified deterministic and capable of producing in-game injuries and score variance across seeds.
- `GronkBowl.Engine.StatsAggregator` derives per-player game stats from the event log, folds them into `PlayerSeasonStats` keyed by (player, year, **team**) so a mid-season trade shows up as two rows, and `CareerHistory(...)` reads a player's whole career, year by year, team by team, off that same table.

- `GronkBowl.Engine.ScheduleGenerator` builds a round-robin schedule (circle method, handles odd team counts with a bye).

- `GronkBowl.Engine.LeagueOrchestrator.ResolveWeek(...)` is the weekly submission flow end to end, with every seed (game and fallback) derived deterministically from season/week/team ids, never supplied by a caller.
- `GronkBowl.Engine.DraftProspectGenerator` / `RookieWageScale` / `DraftOrderCalculator` / `DraftBoard` (an in-memory board type the API's `DraftState` persists a live view of).
- `GronkBowl.Engine.FreeAgencyResolver` and `TradeProcessor`, described above.

## Task 14 (balance tuning) - six rounds, real fixes, genuinely not finished

Each round measured first, fixed the actual root cause, then re-measured - and each fix surfaced a new, deeper layer rather than wrapping the task up. In order:

1. **Ironkin-vs-Aelari.** Aelari measured 0 wins / 0 points across 40 games. Root cause: an uncapped pass-pressure penalty killed the passing game whenever the line battle was lost (which a Strength-poor race always loses), and two racial abilities (Aelari's Featherstep, Skitterkin's Scurry) existed only as text in `RaceProfiles`, never wired in. Fixed both. `BalanceTests` guards it.
2. **The other 5 race pairs.** Skitterkin was losing to everyone due to a 30-point Awareness deficit with no compensating mechanic. Made Scurry mechanically bigger than Featherstep (matching its "extra evasion die" text) - helped vs. Thornhide/Aelari, not vs. Ironkin.
3. **A defense-side Agility lever - tried, overcorrected, reverted** (stacked a third compounding advantage onto Aelari).
4. **Season-simulation harness (`SeasonSimulator`) - found Durability did nothing.** A "do nothing" season broke down to 0-0 for every team by week 6-8 (roster management isn't optional flavor), so the harness auto-signs emergency replacements and tracks how many a race needs as the real cost-of-fragility metric. First run showed Durability did nothing in `CasualtyResolver` beyond a minor duration tweak. Fixed: it now reduces the armor-break roll directly.
5. **Gave Ironkin a real offsetting weakness: Speed**, the one core attribute with zero mechanical hookup anywhere. Added a breakaway mechanic so a meaningfully faster ball carrier can turn a good gain into a big one - slow defenses (Ironkin, Thornhide) can't run it down. Overshot for Aelari (highest Speed in the game) initially, toned down. Also found and fixed the season harness always giving the same team "home"/first-possession for all 16 weeks, compounding a structural edge independent of race.
6. **Fixed the measurement tool itself.** `TestTeamFactory.BuildTeam` (used by every balance test) gave every player identical maximum-ceiling attributes, while `SeasonSimulator`'s replacements rolled realistic 40-75%-of-ceiling variance - any replacement was a categorical downgrade regardless of race, which could snowball into a death spiral unrelated to the actual matchup. Fixed: `BuildTeam` now rolls the same realistic distribution as everyone else.

**Where balance genuinely stands:** six real, verified fixes shipped, each with a permanent regression test (`BalanceTests`, `SeasonBalanceTests`, `CasualtyResolverTests.HigherDurability...`), zero regressions. Re-measuring after round 6 **changed the picture again**: Ironkin-vs-Thornhide flipped (Thornhide now leads), Thornhide-vs-Aelari tightened - but Ironkin-vs-Aelari, verified balanced under the old (flawed) methodology, now shows Ironkin dominating under the corrected one. That's the honest state: the tool is more valid now, but a single 16-week trial per pair is still a small sample against this many interacting mechanisms. Chasing individual pair numbers further without a much larger, systematic trial count would likely repeat the same round-after-round pattern rather than converge - paused here rather than starting a 7th round on that basis.

Next: a larger-scale, systematic balance pass (many trials per pair, controlling one variable at a time) if balance work continues, task 13 (analytics/telemetry), and integration tests against the real database (everything so far is unit-level only).

## Player Progression - Blood Bowl leveling x HC09 hidden potential

A hybrid character-progression system: Blood Bowl's SPP/level-up mechanics, applied to a roster built around a draft/trade/free-agency economy, with an HC09-style hidden development ceiling per player.

- **SPP and leveling** (`GronkBowl.Engine.PlayerProgression`): matches the design brief's thresholds exactly - level 2 at 6 SPP, then 16/31/51/76/121 for levels 3-7, 7 levels max. `SppAwarder` credits SPP after every resolved game (3 for a TD, 2 for a forced turnover or caused injury, 1 per reception, +4 MVP bonus to one participant per team) and separately records `GamesPlayed` per player - split into two methods on purpose, since a player can earn SPP twice in one game (stats + MVP) but should only have `GamesPlayed` incremented once.
- **Level-up rolls** (`GronkBowl.Engine.LevelUpResolver`): 2d6, matching the brief's table - 2-9 a new primary skill, 10 +1 Speed or Armor Value, 11 +1 Agility, 12 +1 Strength; doubles unlock a secondary skill choice instead. `GronkBowl.Engine.SkillAccess` gates which skill categories a player can pick from by position (e.g. a QB's primary category is Passing, an OL's is Strength) the same way the brief's Bretonnian-lineman example gates by team; Mutation skills are Skitterkin-only, and only on doubles, mirroring the brief's Skaven/Chaos Dwarf callout.
- **Development Potential** (`GronkBowl.Domain.DevelopmentProfiles`): 5 named tiers from bust to superstar - Camp Fodder, Replacement Level, Steady Eddie, Pro Bowl Snub, First Ballot Hall of Famer - each with an SPP-rate multiplier and a level ceiling (Camp Fodder tops out at level 2; only First Ballot Hall of Famers can reach level 7 and get a one-time career reroll on a bad level-up roll). Weighted distribution skews toward the middle tiers. A rookie's tier is rolled at creation but hidden (`DevelopmentPotentialRevealed = false`) until they've played 8 games, matching HC09's scouting-uncertainty feel; veterans (demo roster, re-signed free agents) start revealed.
- **API**: `POST /api/players/{id}/levelup/roll` reports the 2d6 result and the player's eligible skill choices without mutating anything; `POST .../apply` takes the raw dice plus the coach's specific skill/stat choice, recomputes the outcome server-side from the dice (never trusts a client-supplied outcome kind), validates the choice is actually eligible, and persists it.
- **Coverage**: 8 of 15 defined skills are mechanically wired into `PlayResolver`/`CasualtyResolver` (Sure Hands, Block, Tackle, Dirty Player, Dodge, Catch, Mighty Blow, plus Guard/Extra Arms/Big Hand reusing those same hooks); the rest (Diving Tackle, Stand Firm, Accurate, Strong Arm, Safe Pass) are fully selectable and persisted but have no gameplay effect yet - tracked via `SkillDefinition.IsWiredIntoEngine` rather than silently pretending they all do something.
- **Verified**: 86/86 tests pass (new: `PlayerProgressionTests`, `LevelUpResolverTests`, `SkillAccessTests`, `SppAwarderTests`), plus a manual end-to-end pass against the live API and Postgres - resolved a real week, rolled a level-up for a player who'd accumulated SPP, applied a skill choice, and re-fetched the roster from scratch to confirm the change actually persisted (not just echoed back in the response).

Not yet started: any frontend UI for leveling up a player (API-only right now), and balance tuning round 7 (left open at the end of task 14, unrelated to this round).

## UI rebuild, phase 1 - match-day core loop and visual identity

The frontend was, until this round, a generic purple/system-ui tabbed admin app - exactly what the project's own guardrail files (`CLAUDE.md`, `GronkBowl-Corrected-Design.md`) explicitly rule out. This phase targets the single most important loop - build a call sheet, resolve a week, watch the result - and makes it actually feel like the Blood Bowl x HC09 fusion, rather than reskinning every screen at once.

- **Backend: the event log now carries real game state.** `PlayResult` gained `Quarter`, `Down`, `DistanceToGo`, `FieldPosition`, `PossessionTeamId`, and `HomeScoreAfter`/`AwayScoreAfter` - the pre-snap situation for every play, captured in `MatchEngine.RecordPlay`. Previously the event log only had play ids, yards, and turnover/score flags - there was no way for a client to reconstruct a drive without re-simulating it. Since `Match.EventLog` is a single `jsonb` column, this needed no migration. A new regression suite (`MatchEnginePlayByPlayTests`) walks every consecutive pair of plays in a resolved game and asserts the down/distance/field-position/possession state machine is internally consistent - and it caught a real, pre-existing bug in the process: a stuffed run could push `FieldPosition` negative with nothing to clamp it, corrupting every play recorded after it. Fixed by clamping to `[1, 99]` the same way the turnover-spot logic already did, since there's no safety mechanic yet to score that properly.
- **Backend: `GET /api/league/matches/{matchId}`** returns a `MatchDetailDto` - team names, final score, the full structured play-by-play (play names resolved from both playbooks, situational state per play), and a structured box score (reusing `StatsAggregator.ComputeGameStats`, the same data `MatchSummaryBuilder`'s text box score already derived, just returned as rows instead of pre-formatted text).
- **Frontend: a real visual identity**, replacing the purple/system-ui token set app-wide (`index.css`, `App.css`) - dark charcoal-navy panels, a field-green action color, a gothic-gold identity/trim color, and a condensed display face (Oswald) for headings and HUD numerals. Applies automatically to every existing tab (Roster/Playbook/Draft/Market/League), not just the new screen.
- **Frontend: `MatchViewer`**, the first animated play-by-play viewer - a scoreboard bug (score/quarter/down-distance/field position), a top-down field strip with an animated ball marker, step/play/pause controls through the real event log, event banners for scores/turnovers/injuries, a running drive log, and the new structured box score as an actual table. Wired into `LeagueView` via a "Watch" action per resolved match, replacing the old raw `summary`/`boxScore` text dump.
- **Frontend: `FormationDiagram`**, a shared top-down formation visualization built from each play's real `{slot, role}` assignment data (there's no spatial data in the backend, so slot positions use a static per-position layout table - an honest approximation, not fabricated routes). Wired into `PlaybookView`, replacing the old bulleted list of `{slot} - {role}` text.
- **Verified**: `dotnet test` passes (93 tests - 9 Domain, 84 Engine, including the 7 new play-by-play state-machine tests), `tsc -b && vite build` type-checks and builds clean, and the new endpoint was checked end-to-end against a real resolved match (down/distance/field position/score progress correctly play to play, a turnover flips possession, a touchdown updates the after-score on the right play).

Explicitly deferred to the next round (per the plan, not an oversight): `CallSheetBuilder` is still dropdown-based (inherits the new visual tokens only, no gamebook/drag-drop redesign yet); Roster/Draft/Market keep their current table-based layouts under the new visual identity; no literal player-sprite animation or route-path visualization, only the slot+role formation abstraction.

## Reachability: playing from a phone

The frontend previously hardcoded `http://localhost:5091` for API calls and both dev servers only bound to loopback, so nothing but the machine running them could ever open the app - a real problem since playtesting happens mostly on a phone. Fixed: `api.ts`'s base URL now follows whatever host the page itself was loaded from (`window.location.hostname`) instead of a hardcoded value; `vite.config.ts` binds Vite to all interfaces on a fixed port (`host: true, port: 5173, strictPort: true`); the API's `http` launch profile binds to `0.0.0.0:5091`; and CORS (dev-only, unauthenticated API) allows any origin instead of one hardcoded origin that broke every time the LAN IP changed. Open `http://<this-machine's-LAN-IP>:5173` from a phone on the same Wi-Fi.

## Live per-down match engine (replaces the whole-game call sheet model)

The match-resolution model changed from "submit a full call sheet for the entire game in advance, the server auto-resolves everything in one batch" to what the game was actually meant to be: **each down is its own decision**. Both coaches (offense and defense, whichever side of the ball they're on) call a play for the current down, async (not real-time - each submits whenever they get to it), it simulates, and the next down waits for the next pair of calls. This also replaces the old fixed `SituationalBucket` taxonomy (RedZone, ThirdAndLong, etc.) with fully custom playbook organization - a coach creates their own named folders and files plays into them however makes sense to them.

- **`PlaybookFolder`** (`GronkBowl.Domain`): `TeamId, Category (Offense/Defense), Name (coach-chosen), PlayIds`. Standing team state, not a weekly submission - CRUD via `GET/POST/PUT/DELETE /api/teams/{id}/folders`. Each demo team is seeded with a "Base Offense"/"Base Defense" folder holding their starter plays so the live-down screen isn't empty on first login.
- **`Match` gained live-state fields**: `Quarter, PlaysRemainingInQuarter, Down, DistanceToGo, FieldPosition, PossessionTeamId, PendingOffensePlayId, PendingDefensePlayId` - meaningful while `!IsResolved`, persisted between requests since a live game now spans many of them instead of resolving in one call.
- **Zero duplication of the actual down-resolution math.** `PlayResolver.Resolve` (one offense play + one defense play in, a `PlayOutcome` out) and the down/distance/score state-transition logic in `MatchEngine.RecordPlay` didn't change at all - `MatchEngine` gained two small adapters (`ToGameState`/`SyncFromGameState`) that convert a `Match`'s persisted live-state fields to and from the same `GameState` the whole-game batch loop already used, plus `ResolveOneDown`, which is just `RecordPlay` + `AdvanceClock` called once instead of in a loop. The old whole-game batch path (`MatchEngine.ResolveGame`, `LeagueOrchestrator.ResolveWeek`, `CallSheet`) is untouched and still exists - repurposed as an "instant-simulate this week" utility (`LeagueView`'s "Simulate Week Instantly" button) rather than the primary way to play, not deleted, since deleting it would have meant rewriting most of the existing Engine test suite for no real gain.
- **`GronkBowl.Engine.LiveMatchOrchestrator`**: `StartMatch` (kickoff state), `SubmitPlay` (records a team's choice for the current down - refuses a second submission from the same side, an illegal play, or a team not in the match), `TryResolveCurrentDown` (resolves once both sides are in), `ForceResolveCurrentDown` (the timeout-fallback mechanic - auto-picks from the missing side's own folders, or any installed play if none fit; exposed as a manual action for now, not yet triggered by a background timer - see "not yet done" below).
- **API** (`LiveMatchController`, `api/league/matches`): `POST .../live/start` (refuses to double-start an already-played matchup), `GET .../{id}/current-down?teamId=` (situation, whose turn, your own folders/eligible plays, scoped to your actual side - offense folders don't leak into a defensive down), `POST .../{id}/submit-play`, `POST .../{id}/force-resolve`.
- **Frontend**: `PlaybookOrganizer.tsx` (folder CRUD, replaces `CallSheetBuilder.tsx`, which is deleted) and `LiveDownView.tsx` (the new primary gameplay screen - scoreboard bug and field strip reused from `MatchViewer`'s visual language, browse-your-folders-and-submit when it's your call, "waiting on the other coach" with polling otherwise, event banners on a resolved down, and a full `MatchViewer` replay once the match ends). `LeagueView` gets a "Play" action per your own unplayed scheduled game instead of only the bulk resolve.
- **Also this round**: Draft and Free Agency are now gated to the offseason (`SeasonPhaseCalculator.IsRegularSeasonComplete`, `GET /api/league/status`, 409s from `DraftController.Start`/`FreeAgencyController.Sign` before every game's played) - separate feedback from the same conversation, unrelated to sync-vs-async but shipped alongside it.
- **Verified**: 102 backend tests pass (new: `LiveMatchOrchestratorTests` covering one-side-submitted-doesn't-resolve, wrong-category/wrong-team refusals, a resolved-down clears pending state, force-resolve fills in from folders or falls back to the whole playbook, and a fully live-played game reaches `IsResolved` with a sane final score); `tsc -b && vite build` clean; a real live match was played several downs deep against the running API via curl - submit-one-side waits, submit-both resolves with the exact expected down/distance/field-position/possession transition (including a fumble correctly flipping possession to the recovery spot), and force-resolve correctly filled in for a side that hadn't answered. The dev database was dropped and recreated for the new schema, which also cleared out this session's own leftover test-simulated games - the "schedule already shows played games" report from earlier in this round was that leftover data, not an engine bug.

**Not yet done** (explicitly deferred, not an oversight): automated timeout enforcement - a coach who never responds currently has to be manually force-resolved by someone, there's no background job sweeping for expired per-down deadlines yet. Folder drag-and-drop / reordering polish. Any further visual pass on `LiveDownView` beyond reusing `MatchViewer`'s existing pieces.
